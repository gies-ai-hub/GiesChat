Deploy

Pushing to main deploys to production. There is no manual step in between.

flowchart LR
  P[git push main or staging] --> GH[GitHub Actions · azure-deploy.yml]
  GH -->|docker buildx| ACR[ACR · dlacrgieschat.azurecr.io/gieschat/api]
  ACR --> W{publish profile}
  W -->|main| PROD[Web App gieschat]
  W -->|staging| STG[gieschat-staging slot]

What triggers it

.github/workflows/azure-deploy.yml runs on pushes to main and staging that touch api/, client/, packages/, librechat.yaml, the Dockerfile or a few other paths. Docs-only changes, like this site, don't deploy.

What it does

  1. Builds the image and pushes it to ACR as gieschat/api:<sha>, also tagged latest (main) or staging.
  2. Deploys with azure/webapps-deploy@v3 to the Web App gieschat. The target slot comes from the publish-profile secret (AZURE_WEBAPP_PUBLISH_PROFILE or AZURE_WEBAPP_STAGING_PUBLISH_PROFILE). Don't add slot-name.

Production: gieschat.azurewebsites.net · Staging: gieschat-staging.azurewebsites.net

The image

The Dockerfile uses Node on Alpine with jemalloc, plus Python and uv/uvx for the Canvas MCP. It runs npm ci, then npm run frontend (packages + client), prunes dev dependencies and serves on port 3080 with npm run backend. MongoDB, Meilisearch and the RAG API run outside the image.

Separate deploys

The MCP servers in infra/ deploy on their own: pptx-mcp through .github/workflows/pptx-mcp-deploy.yml, and ms365-mcp as described in its README.

Before pushing to main: run the tests for what you touched, try risky changes on staging first, and remember faculty may be mid-class.
